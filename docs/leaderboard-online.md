# План: онлайн-доска лидеров (локальный + онлайн режимы)

Дата: 2026-10-18. Статус: план сохранён, реализация не начата.

## Исходная точка

Сейчас рекорды — `ResultsService` поверх `IKeyValueStore` (файл на
Windows/Android, localStorage на Web): топ-10 локально, имя игрока
сохраняется в настройках. Цель — второй источник рекордов (онлайн),
не ломая локальный режим:

- В таблице рекордов переключатель «Локальные / Онлайн» (или две вкладки).
- Локальный режим — по умолчанию, работает офлайн.
- Онлайн: показ глобального топа + отправка своего результата после игры,
  корректная обработка «нет сети».

Ключевое ограничение: GitHub Pages статический, а Web-версия по HTTPS
не сможет обращаться к HTTP-API (mixed content блокируется браузером).
Поэтому API для Web-версии должен быть доступен по HTTPS.

## Варианты онлайн-реализации

| Вариант | Что это | Плюсы | Минусы |
|---|---|---|---|
| 1. Firebase (Firestore / Realtime DB) | Готовый BaaS от Google, клиент ходит по REST прямо из игры | Не нужен свой сервер, бесплатный тариф, все платформы, масштабирование из коробки | Аккаунт Google, правила безопасности, vendor lock-in, без правил — запись мусора кем угодно |
| 2. Supabase | BaaS на PostgreSQL с готовым REST/RPC | Открытый код, SQL, можно позже self-host, бесплатный тариф | Настройка RLS, чуть больше ручной работы |
| 3. Игровые бэкенды: PlayFab / LootLocker / Nakama | Сервисы с готовыми leaderboards | Топ-N, сезоны, профили из коробки; PlayFab имеет C# SDK | Избыточно для одной таблицы, доп. SDK/учётка, лимиты бесплатных тарифов |
| 4. Собственный API: ASP.NET Core Minimal API + SQLite | 2-3 endpoint'а, один маленький сервис (~100-150 строк) | Полный контроль, тот же C#, хостинг где угодно (домашний Apache, VPS, Render/Fly.io) | Нужны хостинг, HTTPS, обслуживание, бэкапы |

Античит: любой вариант, где клиент шлёт «имя + очки», позволяет подделку.
Для игры «для своих» достаточно серверной валидации (диапазон очков,
длина имени, rate limit по IP). Проверка честности партии по ходам
возможна только в варианте 4 и на порядок сложнее — в v1 не закладывать.

Рекомендация:
- без своего сервера — Firebase (вариант 1), самый быстрый путь;
- свой код и контроль — вариант 4, хостинг с HTTPS из коробки
  (Render/Fly.io) или домашний сервер с публичным доменом + Let's Encrypt.
  Домашний HTTP-only годится только для Windows/Android (не для Web).

## Этапы внедрения (общие для любого варианта)

### Этап 1. Абстракция и UI-каркас (без сети)
- `ILeaderboardSource` с реализациями: локальная (текущий ResultsService)
  и онлайн-заглушка.
- Переключатель «Локальные/Онлайн» в таблице рекордов, состояние
  загрузки и сообщение об ошибке; выбор режима по умолчанию в настройках.
- Локализация ru/en новых строк.

### Этап 2. Серверная часть (по выбранному варианту)
- Контракт: `GET /api/scores?top=10` → `[{name, score, dateUtc}]`;
  `POST /api/scores` с теми же полями; валидация, топ-N, rate limit.
- Вариант 4: Minimal API + SQLite, Dockerfile, инструкция развёртывания.
- Варианты 1/2: проект и правила доступа в консоли сервиса.

### Этап 3. Сетевой клиент в игре
- `OnlineResultsService` на HttpClient (Windows/Android/WASM), таймауты,
  обработка ошибок.
- Отправка результата после рекорда, кэш последнего онлайн-ответа
  для офлайна, CORS для Web-версии.
- Адрес API — в настройках/конфиге, не хардкод.

### Этап 4. Тесты и документация
- Юнит-тесты клиента через подменённый HttpMessageHandler (ответ,
  таймаут, битый JSON); тесты API для варианта 4.
- Обновление AGENTS.md, README; контроль, что CI и релизы не сломались.

### Этап 5. Защита от злоупотреблений (минимум)
- Ограничение частоты записей, максимальная длина имени, фильтрация
  символов, потолок очков, даты в UTC.

## Порядок старта

Этап 1 не зависит от выбора варианта — можно начать с него.
Выбор варианта (Firebase vs собственный API) нужен к этапу 2.
